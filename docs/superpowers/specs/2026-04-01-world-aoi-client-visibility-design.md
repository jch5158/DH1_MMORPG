# 월드 AOI·클라이언트 가시 오브젝트 설계 (1단계: 셀 집합 diff)

## Overview

맵을 **그리드(격자)** 로 나누고, 각 칸은 **셀**이다. 플레이어(또는 시점 주체)의 현재 셀과 **AOI 반경(셀 단위)** 으로 정의된 **영향권(주변 셀 집합)** 안에 있는 엔티티만 클라이언트에 **가시**로 유지한다.  
**1단계**에서는 플레이어 이동 등으로 **이전 영향권 셀 집합과 현재 집합의 차이(diff)** 를 내어, 들어온 오브젝트는 **추가**, 나간 오브젝트는 **제거** 알림으로 클라 가시 집합을 맞춘다.

- **현재**: 멀티 클라이언트 관련 재현 버그는 없음.
- **향후**: 약 5,000 근처 **더미 클라이언트** 부하 검증 예정 → 병목·가정을 문서로 고정.
- **토폴로지**: 단일 WorldServer 집중 / 샤드 분산 **둘 다** 시나리오로 검토 가능(본 스펙은 **월드 인스턴스 하나** 안의 AOI 규칙에 초점).

## 용어

| 용어 | 의미 |
|------|------|
| 그리드 | 맵을 셀로 나눈 **전체 분할 체계** |
| 셀 | 그리드의 **한 칸** (좌표 `(cx, cy)` 등) |
| 영향권 | 관찰 주체 셀 기준 **AOI 반경 안의 셀들의 합집합** |
| 가시 오브젝트 | 해당 클라이언트에 **스폰·동기화 대상으로 유지**되는 엔티티 집합 |

기존 `GridManager`의 `GetCellsInRange` / `GetObjectsInRange` / `mAoiRange` 는 본 설계의 **그리드·영향권** 층과 대응한다.

## 선택한 접근: 1번 (이동 시 셀 집합 diff)

### 동작 요지

1. 각 세션(플레이어)마다 **현재 가시 엔티티 집합**을 유지한다.
2. 관찰 주체의 **기준 셀**이 바뀌거나, AOI 규칙이 바뀌거나, **초기 진입·전체 리싱크**가 필요할 때:
   - `이전 영향권 셀 집합` vs `현재 영향권 셀 집합`을 비교한다.
   - 각 셀에 속한 오브젝트를 조회해 **추가 후보 / 제거 후보**를 만든 뒤, 집합 연산으로 **실제 Add / Remove** 를 결정한다.
3. 월드 오브젝트가 **스폰·이동·디스폰**되면, 그 오브젝트가 위치한 셀(및 필요 시 이전 셀)이 **어떤 플레이어의 영향권과 교차하는지**에 따라 해당 플레이어에게 Add 또는 Remove 를 보낸다.

### 장단점 (고정)

- **장점**: 구현이 직관적이고, `GridManager`와 자연스럽게 맞물린다.
- **단점**: 셀 **경계를 빠르게 오가면** Add/Remove 가 잦아질 수 있음 → 추후 **히스테리시스·배치 전송(3번 옵션)** 을 같은 계약 위에 얹을 수 있음.
- **복잡도**: **2번(셀 구독)** 보다 낮음. 부하가 커지면 **2번으로 내부 교체**하는 로드맵을 허용한다.

## 마이그레이션 경계 (1 → 2)

다음을 지키면 추후 2번으로 갈아타기 쉽다.

- **단일 책임**: “누구에게 어떤 엔티티를 보이게 할지”는 **한 모듈(또는 명확한 서비스 경계)** 에서만 결정한다. 월드 전역에 `GetObjectsInRange` + 직접 송신이 흩어지지 않게 한다.
- **바깥 계약 고정**: 클라이언트·게이트웨이가 의존하는 것은 **Add / Remove / (필요 시) 전체 스냅샷** 의미이지, “내부가 diff인지 구독인지”가 아니다.
- **전환 시**: 내부 구현 교체 후 **한 번의 전체 리싱크(스냅샷)** 로 클라 집합을 재동기화할 수 있어야 한다.

## 데이터 흐름 (논리)

1. **플레이어 이동** → 기준 셀 변경 가능 → 영향권 셀 집합 diff → 대상 엔티티 Add/Remove.
2. **오브젝트 추가** (`GridManager::AddObject` 등) → 소속 셀이 알려짐 → 그 셀이 각 플레이어 영향권에 포함되면 Add.
3. **오브젝트 제거** → 영향권에 있던 플레이어에게 Remove.
4. **오브젝트 셀 이동** → 이전 셀에서 벗어난 플레이어에게 Remove, 새 셀로 들어온 플레이어에게 Add (또는 통합 diff).

## 오류·경계 조건

- **패킷 순서**: 늦게 도착한 Remove 가 먼저 도착한 Add 보다 먼저 처리되면 클라가 꼬일 수 있음 → **엔티티별 버전/세대** 또는 **idempotent 처리(이미 없으면 무시)** 규칙을 프로토콜 설계 시 명시.
- **로그인 직후**: 초기 가시 집합은 **스냅샷 한 번**으로 채우고, 이후 diff만 보내는 방식이 단순하다.
- **게이트웨이·월드 분리**: 세션 단위로 “어느 월드의 어느 엔티티 집합”인지 식별자가 일관되어야 한다.

## 부하 검증 (5,000 더미) 시 관찰 지표

- 틱당 **diff 계산 횟수**, **셀당 평균 엔티티 수**, **플레이어당 초당 Add+Remove 횟수**.
- **송신 큐 깊이**, WorldServer **CPU**, (해당 시) **Gateway** 병목.
- 단일 프로세스 한계에 근접하면 **샤딩** 시나리오로 동일 지표를 **인스턴스당 인원**으로 나누어 비교.

## 범위 밖 (본 스펙이 정하지 않는 것)

- 정확한 패킷 ID·프로토콜 필드 배치(별도 프로토 문서).
- 언리얼 쪽 액터 풀·리플리케이션 세부(클라 구현 플랜에서 다룸).
